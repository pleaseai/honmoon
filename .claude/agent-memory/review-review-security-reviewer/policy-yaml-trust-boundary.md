Policy YAML in honmoon is **trusted author input**, not untrusted data.

**Why:** since #202 (PR #217) the only load path is `honmoon-cli/src/main.rs` `load_policy()`, which every command taking a policy path goes through — `gateway()` lost its own inlined `std::fs::read_to_string(&config)` → `Policy::from_yaml`, so `load_policy` is now the single non-test `from_yaml` caller in `crates/*/src`; `honmoon-mgmt/src/lib.rs` registers `/api/policy` with `get(get_policy)` only — there is no POST/PUT policy upload or hot-reload route. So rule names, endpoint names and conditions are written by whoever owns the config file, i.e. the same principal that runs the gateway.

**How to apply:** do NOT report log injection / ANSI-forging / information-disclosure findings for `tracing::warn!` calls in `Policy::from_yaml` (`warn_undefined_endpoints`, `warn_shadowed_rules`) that interpolate `rule.name` / `rule.endpoint` — the strings are author-controlled. Same for O(n^2) load-time passes over `policy.rules`: the rule list is a hand-written file, not attacker-sized. Re-verify this memory if a policy-write route (reload/upload) ever appears in `honmoon-mgmt` — that would move the boundary and make all of the above live.

**#191 (PR #197) addition — the load is now fail-hard, and every caller propagates it.** `Policy::from_yaml` ends with `CompiledConditions::compile` + `validate_compiled_conditions`, returning `Error::UncompilableRuleConditions { rules }` (index + name + raw condition text per offending rule) when any CEL condition does not compile. Verified, but re-resolve the anchors rather than trusting them — an earlier revision of this note carried line numbers that its own repository had already moved past. Named symbols instead: since #202 the only non-test caller is `load_policy()`, reached from `gateway()`, `run()` and `policy_validate()`; all three use `?` into `fn main() -> anyhow::Result<()>`, so a bad policy exits non-zero — `run()` never spawns the child, `gateway()` refuses before binding any listener or opening the audit log. The error text therefore reaches **stderr only**: no mgmt HTTP body (the load precedes `honmoon_mgmt::serve`), no audit event, and `CompiledConditions::compile` has no **production** caller besides `from_yaml` (three `#[cfg(test)]` callers in `engine.rs` aside), so removing `warn_inert_rule` *from `compile`* lost no operator-facing signal — the hard error names strictly more than the dropped warnings did. Note what was **not** removed: `warn_inert_rule` still exists and still fires on the evaluate path via `compile_condition`, for a `Policy` built in code or a `Rule::condition` reassigned after load. Do not read this as "the inert-rule warning is gone". Docs carry an explicit "a gateway that starts today may stop starting" warning in `wiki/getting-started/policy-authoring.md`; and note the validation-only command now **exists**: #198 landed as `honmoon policy validate`, which loads and exits without resolving the mgmt token, binding a listener or opening the audit log. (`honmoonctl validate` is still a stub and the JSON Schema still does not parse CEL. `honmoon gateway --config <file>` on a *valid* policy still goes on to serve, and still resolves the mgmt token first, so it can write `~/.honmoon/mgmt-token` even on a run whose policy fails — which is the side effect `policy validate` exists to avoid.)
